# 决策记录：首发策略、fixed 组拆分、演进路线重设计

> 三个决定：**直接发 0.3.0** · **`blocks` 搁置** · **`fixed` 组按档 B 拆分**
>
> 促成它们的事实是同一个：12 个包都停在 0.2.0，**一个都没发布过**。
> 也就是说此前所有「演进」讨论都还停留在构建阶段，路线图却已经写到「推广治理」了。

---

## 一、`fixed` 组是什么，为什么要拆

### 它现在做的

`.changeset/config.json` 原先把**全部 12 个发布包**放进同一个 `fixed` 组：

> 组内任何一个包有变更 → 全部 12 个取**最高**的 bump 级别，统一到同一个版本号。

内部依赖写的是 `workspace:^`，发布后是 `^0.3.0` 这样的**范围**（不是精确版本）。

### 它换来的三件事

| 收益 | 说明 |
|---|---|
| 任意两包版本相同 | 消费者不用算组合 |
| 排除契约错配 | `adapter-core@0.3` 配 `adapter-vant@0.1` 这种组合不存在 |
| 破坏性变更自动协调 | 改 core 契约要连带 3 个适配器，fixed 让它成为一个动作 |

### 它付出的代价（实测）

**① 版本号失去逐包含义**

拆之前 12 个包全是 `0.2.0`，但变更量差异极大：

```
tokens/CHANGELOG.md        0.2.0 ·  1 条
shared/CHANGELOG.md        0.2.0 ·  1 条
adapters/vant/CHANGELOG.md 0.2.0 ·  5 条
components/CHANGELOG.md    0.2.0 ·  7 条
```

同一个版本号，背后是 1 条和 7 条的区别。**消费者从版本号读不出「我这个包变了多少」。**

**② 改一个包 = 发 12 个包**

只改 `tokens` 一个色值也要全量 publish。而 `publish-all.mjs` 是顺序发布，
**任一个失败即中断** —— 发布面越大，失败概率越高。

**③ bump 级别被拉平**

组内取最高。一个包 minor，12 个全 minor ——
**「破坏性变更」与「小修补」在版本号上不可区分**。

### 拆开的收益，精确表述

> **让补丁级修复能单独发布，而不是每次都变成 12 个包的整组事件。**

关键前提：因为是 `workspace:^`（`^0.3.0`），**补丁级 bump 不越出范围，不会连带升下游**。

| 场景 | 拆前 | 拆后 |
|---|---|---|
| 修 `tokens` 一个色值 | 12 个包全发 | **只发 tokens** |
| 修 `adapter-vant` 一个 bug | 12 个包全发 | 发 vant（+ 需要时 core） |
| 改 `adapter-core` 契约 | 12 个包全发 | **仍要协调**（`^0.x` 跨 minor 会断） |

**破坏性变更仍然需要协调——但那种变更本来就该协调。**
收益集中在「小修补的发布面从 12 缩到 1」。

## 二、为什么选档 B，而不是全拆或不动

### 包的真实依赖结构

```
tokens, shared                   ← 零内部依赖
  └─ data                        ← 只依赖 shared
  └─ adapter-core ──┬─ adapter-element-plus / vant / naive-ui
  └─ chart-core ────┴─ dashboard / screen
       └─ components ← 汇点，依赖上面四个
resolver                         ← 零内部依赖
```

`components` 是**汇点**：任何上游 minor 都会逼它重发。
所以「12 个包各自独立」是假象。

### 三个档位

| 档 | 做法 | 判断 |
|---|---|---|
| A | 保持不动 | 零成本；但小修补永远整组发布 |
| **B** | 拆出零耦合的三块：`tokens` / `shared` / `data` 一组独立，`resolver` 独立，其余 8 个 UI 栈包保留 fixed | **采用** |
| C | 12 个全拆 + `@fbkworks/kit` 元包锁兼容组合 | pre-1.0 阶段破坏性变更是常态，正好是 fixed 最值钱的场景，现在做不划算 |

### 采用 B 的理由

1. **成本接近零**：拆出去的四块不依赖任何人，拆开不制造协调负担
2. **覆盖了最高频的场景**：色值、工具函数、resolver 的修补都可以单发
3. **保留了真正的耦合**：`ADAPTER_API_VERSION` 把 UI 栈内部绑在一起，那部分就该锁步

### 已知的缺口（不修，但要说清）

`ADAPTER_API_VERSION` 只在 **adapter ↔ adapter-core** 之间有运行时校验。
**`components` ↔ `adapter-core` 没有** —— 它直接 `import type` 并调 `useAdapter`。

不过所幸这两者仍在同一个 fixed 组里，所以缺口暂时不暴露。
将来若要把 `components` 也拆出去，必须补其一：`peerDependencies`、运行时校验、或元包。

## 三、首发：直接发 0.3.0

待落地的 changeset 里有多个 minor（可选原语层、Empty 移除、图表零件下沉、能力位审计），
按 fixed 取最高级别的规则，**12 个包自然落到 0.3.0**。

四个基础设施包（`tokens` / `shared` / `data` / `resolver`）本次没有代码变更，
但加了一条**一次性** changeset 把版本对齐到 0.3.0，避免首发时
「kit 说是 0.3.0，tokens 却是 0.2.0」的噪音。

> 从 0.4.0 起它们各自独立演进，这条对齐 changeset 不再重复。

顺带把 `@fbkworks/consumer-smoke`（`tests/consumer` 的私有包，从不发布）
加进 `ignore`，之前它会被连带 bump。

## 四、`blocks` 为什么搁置

反模式清单第 20 条：

> **地基没稳就做 blocks** —— 页面级组合会倒逼业务组件 API 过早定型

这一轮把地基的**机制**做稳了（清单可生成、能力位可校验、契约可演进）。
但「稳」还有另一半：**API 有没有被真实使用者打磨过**。

当前下载量是 0，没有任何外部消费方。此时做页面级组合，
正是那条反模式说的风险——把还没被验证的组件 API 固化成更上层的契约。

**决定：搁置，等首发后积累到 2～3 个真实接入方再评估。**

## 五、演进路线怎么改

原 P0/P1/P2 回答的是「先做什么再做什么」。现在 12 包 10 组件 3 适配器都在，
**构建阶段已经结束**。继续用那张图会把「已完成」和「待办」混在一起。

改成四段「发布与治理」，每段带**可验证的完成判据**（本项目的规矩：没有门禁的「完成」不算完成）：

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| **M1 首发** | 0.3.0 上 npm | registry 可安装；空项目按文档接入跑通四类页面；改 patch 能自动发版且 tag 正确 |
| **M2 契约稳定** | 可选层实操一次；公开 API 快照；清能力位欠债 | 新增原语不升 `ADAPTER_API_VERSION`；`pnpm check:capabilities` strict 转绿（现 11 条 `unverified`） |
| **M3 覆盖扩展** | 移动端能力补齐；更多图表类型 | 走可选层 / 共享零件，不复制 |
| **M4 治理成熟** | 视觉回归进 CI；a11y；包体积数据 | `scripts/visual/` 的 4 个脚本进 CI（现在 0 个）；全库 aria 覆盖 |

`blocks` 不进任何阶段，标注「待真实消费方反馈」。
